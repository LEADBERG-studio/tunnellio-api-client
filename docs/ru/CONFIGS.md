# Модель конфигурации

## Задача
Клиент умеет стартовать двумя способами:

- от **конфига по умолчанию**, которым он управляет сам;
- от **клиентского конфига**, выбранного явно.

Порядок запуска важен:

1. определить целевой конфиг;
2. если флаги командной строки меняют значения, решить, переписывать ли файл;
3. собрать итоговый снимок конфига;
4. запуститься от этого снимка.

## Имена туннелей
У каждого управляемого туннеля есть имя.

- явное: поле `connect.name` в конфиге или флаг `--name`;
- неявное: порождается само, если имя не задано.

Дальше имя используется для перечисления туннелей, запроса состояния, адресной остановки, чтения runtime-конфига и получения серверных параметров подключения после запуска.

## Зачем нужно чтение конфига по имени
Для постоянных доменов вызывающая программа обычно и так знает нужное имя хоста. Для случайных и эфемерных — нет.

В таких случаях единственный рабочий порядок: сначала поднять туннель, потом прочитать итоговые серверные данные. Ради этого клиент и хранит снимки, доступные по имени запуска.

Правило на практике:

- запускать по конфигу или флагам;
- опознавать туннель по имени запуска;
- забирать итоговые данные командой `show-config --name <имя>`.

## Файлы конфигурации
### Образец в проекте
- `config.example.json`

В нём перечислены все поддерживаемые поля.

### Конфиг по умолчанию
- `~/.tunnellio/default-launch.json`

Поведение:

- если `--config` не передан, этот конфиг выбирается сам;
- если переданы флаги, клиент сначала обновляет этот файл;
- затем запускается уже от обновлённого файла;
- если в файле уже есть сохранённые значения и новых флагов нет, запуск без аргументов идёт прямо от него.

### Клиентские конфиги
Рекомендуемый каталог: `~/.tunnellio/configs/`.

Держать их можно где угодно и передавать полным путём.

## Приоритет и перезапись
### Без явного конфига
Если `--config` не передан:

- целью считается конфиг по умолчанию;
- флаги переписывают его автоматически;
- запуск идёт от переписанного файла.

### Явный конфиг вместе с флагами
Если передан `--config path.json` и одновременно заданы флаги:

- файла нет — он создаётся, запуск идёт от него;
- файл есть и его содержимое изменилось бы — клиент спрашивает, переписывать ли;
- `--config-overwrite yes` — не спрашивает и переписывает;
- `--config-overwrite no` — файл не трогает, но в текущем запуске значения флагов главнее совпадающих полей конфига.

## Управление по имени
### Все туннели
```powershell
.\tunnellio.exe status
```

### Состояние одного
```powershell
.\tunnellio.exe status --name prod-api
```

### Остановить один
```powershell
.\tunnellio.exe stop --name prod-api
```

### Прочитать сохранённые параметры подключения
```powershell
.\tunnellio.exe show-config --name prod-api
```

## Поля нового серверного контракта
В конфиге запуска есть переключатели сессии и авторизации, которых требует новый контракт сервера. Для `plan` и `connect` важны:

- `requestedAuthMode`
- `connectionMode`
- `oauthClientPolicy`
- `runtimeName`
- `useDiscovery`
- `sessionStrategy`
- `enablePkce`

Что это значит на практике:

- `requestedAuthMode` просит у сервера `legacy`, `oauth` или другой поддерживаемый режим;
- `connectionMode` закрепляет транспорт, когда сервер поддерживает несколько путей;
- `oauthClientPolicy` говорит серверу, какую стратегию OAuth-клиента применить;
- `runtimeName` даёт серверу и локальному реестру один и тот же устойчивый идентификатор;
- `useDiscovery` включает или выключает загрузку OAuth discovery;
- `sessionStrategy` описывает, как обходиться с открытием и возобновлением сессии;
- `enablePkce` просит подготовить поток OAuth с поддержкой PKCE.

Главное правило: запрошенный режим — это намерение, а не подмена серверной истины. Клиент записывает и проверяет тот `authMode` и `connectionMode`, который вернул сервер.

## Файлы реестра запусков
- `~/.tunnellio/state/runtimes/<имя>.json` — состояние запуска;
- `~/.tunnellio/state/runtimes/<имя>.config.json` — снимок конфига с данными подключения;
- `~/.tunnellio/state/runtimes/<имя>.stop` — сигнал мягкой остановки.
